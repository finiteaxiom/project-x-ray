# 架构决策记录 0001：采用本地优先的证据图架构

- 状态：已接受
- 日期：2026-09-19

## 背景

Project X-Ray 必须在解释陌生代码的同时保持结果可审计。纯 LLM 或检索增强生成方案可能产出看似合理、实际上缺乏依据的架构和执行路径；而 V1 也不可能实现一个达到编译器精度、支持所有语言的通用分析器。产品还会处理私有源码，因此没有必要的远程传输不可接受。

## 决策

采用本地优先的桌面架构，并把版本化证据图作为系统的事实来源。

- 确定性分析器负责创建节点、边、源码范围和置信度元数据。
- SQLite 为每个导入项目的快照演进链保存一份图数据。
- 查询引擎负责检索范围受限的证据子图。
- LLM 提供商只接收最小化证据包，可以解释或辅助评分，但不得创建已验证的图事实。
- V1 为 JavaScript、TypeScript 和 Python 提供一等语义适配器。
- 导入的代码只进行解析，索引过程中绝不执行。

## 影响

正面影响：

- 每项结论都能追溯到源码；
- 核心导航功能可以离线工作；
- 隐私边界和数据删除行为清晰可理解；
- 分析器与 LLM 提供商可以独立演进。

负面影响：

- 对动态代码而言，静态路径必然不完整；
- 语言适配器需要维护大量样例仓库测试；
- SQLite 图查询需要精心设计索引并限制遍历范围；
- 解释功能必须显式封装证据，不能简单地把整个仓库直接交给模型。

## 重新评估条件

只有在完成索引与查询优化后，实测的 V1 规模图查询仍无法达到约定性能预算时，才重新评估数据库选择。如果工作线程隔离无法应对解析器崩溃或资源限制，则重新评估进程模型。不得仅凭个人偏好推翻本决策。
