# Project X-Ray V1 架构设计

状态：**已批准，开发中**  
日期：2026-09-20

## 1. 产品判断

Project X-Ray 不应该是“把整个仓库塞给 LLM，让它写一篇看似合理的总结”。它应当是一个有证据链的代码认知系统：静态分析负责建立事实，图查询负责寻找路径，LLM 负责把已经找到的证据组织成人能理解的解释，所有权模式再验证用户是否真正掌握这些证据。

核心闭环是：

```text
导入项目
  -> 建立可追溯的代码事实图
  -> 浏览架构/调用/数据/变更路径
  -> 基于事实解释功能
  -> 回到源码回答问题
  -> 暴露认知盲区
  -> 定向复习与再次测试
```

## 2. V1 成功标准

V1 不以“支持多少语言”作为首要成功指标，而以以下三件事为准：

1. 对 JS/TS/Python 项目，用户可以从架构图中的模块一路跳到真实文件和源码行；
2. 对一个受支持的调用或 Git diff，系统能给出可复核的路径、证据与不确定性，而不是无引用的总结；
3. 所有权模式能证明用户会在源码中定位入口、关键分支、数据变换和副作用。

## 3. 推荐技术栈

| 区域 | 选择 | 原因 |
| --- | --- | --- |
| 桌面壳 | Electron | Node 文件系统、Git、Worker 与解析器生态成熟；V1 交付速度优先 |
| UI | React + TypeScript + Vite | 适合复杂交互、图视图与代码阅读器，类型可与主进程共享 |
| 组件与样式 | Tailwind CSS + Radix primitives | 快速建立可访问的设计系统，避免重型组件库锁定视觉 |
| 状态/请求 | Zustand + TanStack Query | 本地交互状态和异步任务状态分离 |
| 代码查看 | Monaco Editor（只读为主） | 源码定位、语法高亮、行选择与引用体验成熟 |
| 图可视化 | Cytoscape.js + ELK 布局 | 支持大图交互、子图、分组和分层布局 |
| 本地 API | Electron typed IPC；预留 localhost service adapter | V1 少一层部署复杂度，同时保持未来 Web/CLI 可迁移性 |
| 解析基础 | Tree-sitter | 错误恢复、增量解析和多语言统一入口 |
| TS/JS 语义增强 | TypeScript Compiler API | 模块解析、类型/符号与跨文件引用比纯语法树更可靠 |
| Python 语义增强 | Python `ast` + 自建解析 worker | 标准 AST 稳定；负责定义、引用、控制流和有限数据流提取 |
| 图存储 | SQLite + FTS5 | 本地单文件、事务成熟；V1 图规模用关系表与递归查询足够 |
| 数据访问 | Kysely + better-sqlite3 | SQL 可控且类型安全；适合图边和证据查询，不隐藏查询成本 |
| Git | 系统 Git + 受控参数封装 | 兼容凭据管理器、submodule 与真实仓库行为；不重新实现 Git |
| 后台任务 | Node Worker Threads + 独立 Python worker | 避免阻塞 Electron；为任务取消和崩溃隔离留边界 |
| Schema | Zod + JSON Schema | 校验 IPC、数据库反序列化与 LLM 结构化输出 |
| LLM | Provider adapter；首个实现使用 OpenAI Responses API | 支持结构化输出和自定义工具；核心图谱不依赖云模型 |
| 测试 | Vitest + Playwright + fixture corpus | 覆盖纯逻辑、Electron UI 与分析器金标项目 |
| Monorepo | pnpm workspaces + Turborepo | 共享类型明确，缓存构建；复杂度可控 |

### 为什么 V1 不用 Neo4j

V1 是单机、本地优先产品。SQLite 已足够保存数十万到数百万级节点/边，并能用索引、递归 CTE 和应用层遍历完成限定深度查询。直接引入图数据库会增加安装、迁移、打包和隐私成本。只有在真实基准证明 SQLite 的子图查询无法达到交互要求时才升级。

### 为什么暂不以 Rust 为主分析核心

Rust 能带来速度和内存优势，但 V1 最大风险是“分析语义是否正确、产品闭环是否成立”，而不是极限吞吐。TypeScript 主体更利于 Electron 集成和快速校正分析器。Graph IR 与 analyzer contract 必须保持语言无关；未来可把热点解析或查询替换为 Rust/N-API，不改变产品层。

## 5. 图中间表示：统一事实模型

### 5.1 核心节点

- `Repository`（仓库）：导入来源、根路径、忽略规则；
- `Snapshot`（快照）：提交 SHA 或工作区内容指纹；
- `File`（文件）：路径、语言、哈希、解析状态；
- `Module`（模块）：语言语义中的模块或包；
- `Symbol`（符号）：函数、类、方法、变量、字段、路由、组件；
- `ExternalDependency`（外部依赖）：npm、Python 或系统依赖；
- `Endpoint`（端点）：HTTP、IPC、CLI 或事件入口；
- `DataEntity`（数据实体）：请求体、DTO、模型、数据库实体等可识别结构；
- `ChangeSet`（变更集）：Git 比较基准与变更文件或行；
- `Evidence`（证据）：源码范围、分析器、规则、置信度。

### 5.2 核心边

- `CONTAINS`, `DEFINES`, `IMPORTS`, `EXPORTS`, `DEPENDS_ON`；
- `CALLS`, `READS`, `WRITES`, `RETURNS`, `PASSES_TO`；
- `HANDLES`, `EMITS`, `PERSISTS`, `QUERIES`；
- `CHANGED`, `MAY_AFFECT`, `DERIVED_FROM`。

所有边都必须带 `snapshot_id`（快照标识）、`provenance`（来源）和 `confidence`（置信度）。动态调用无法解析时，保存“未解析目标”和原因，并保留可见占位节点，不得伪造目标。

### 5.3 稳定标识

文件标识来自“仓库 + 规范化路径”；符号标识来自与快照无关的逻辑键（语言、模块、限定名、签名），并辅以内容指纹。源码位置变化时尽量保持逻辑身份；出现歧义时新建符号并记录替代候选，避免把两个同名函数错误合并。

## 6. 索引管线

```text
获取源码
 -> 根目录约束 / 忽略规则 / 二进制和秘密文件过滤
 -> 清单文件与语言检测
 -> 增量解析文件
 -> 提取符号和语法事实
 -> 解析导入与导出
 -> 按语言增强语义
 -> 生成归一化节点、边和证据
 -> 再次核验工作区内容哈希
 -> 以事务方式提交图和不可变源码快照
 -> 推导模块分组、入口和搜索索引
 -> 可选的 LLM 标签与摘要
```

每阶段都必须可取消、可重试，并报告进度。当前采用全量重新索引。解析错误不应使整个项目失败：文件记录 `partial`（部分成功）或 `failed`（失败），图中明确显示缺口。取消或提交前哈希核验失败不会替换上一份完整快照；进入 SQLite 提交事务后以事务完成为准。

### 快照读取规则

- 图、解释、题目、答案和源码请求都显式绑定仓库与快照；
- 源码查看器读取索引时保存的不可变内容，不读取后来的工作区内容作为证据；
- 每次打开证据和提交答案时重新核验相关工作区内容，文件监听只用于改善响应速度，不是正确性来源；
- `current` 表示内容哈希一致，`stale` 表示内容变化，`missing` 表示工作区文件不存在；
- 旧快照过期后仍可查看历史证据，但解释、差异和答题必须更新索引后继续。

### JS/TS 策略

- Tree-sitter 负责快速结构解析和不完整代码；
- TypeScript Compiler API 读取 tsconfig 或 jsconfig，负责路径别名、模块解析、符号和引用；
- React 事件、Express/Fastify 路由等框架关系由独立的框架适配器生成 `inferred` 或 `verified` 事实，不能污染通用语义层。

### Python 策略

- 使用受控的 Python 工作线程调用标准库 `ast`，不得导入被分析项目；
- 解析包、模块、定义、调用表达式、读写集合、返回值和控制流；
- 通过 `pyproject.toml`、`requirements*.txt`、导入路径与项目结构解析依赖；
- 猴子补丁、动态导入、装饰器注入等必须显式降低置信度。

## 7. 六个功能如何落地

### 7.1 导入本地/Git 项目

本地目录通过系统目录选择器导入。Git 地址克隆到应用管理的工作区缓存，默认使用浅克隆；私有仓库沿用系统 Git 凭据管理器。导入过程只读分析，不运行仓库脚本。

导入完成页必须显示：语言构成、文件/符号/边数量、忽略内容、解析失败、不支持的文件和快照标识。

### 7.2 架构图

先由确定性规则找到入口、清单文件、模块边界和依赖分组，再让 LLM 为已经存在的分组生成简短标签与职责描述。图上任何模块都可以展开到文件或符号，并显示“为什么被归到这里”。

默认分层：产品功能面 -> 入口 -> 模块 -> 文件 -> 符号。避免一次渲染整个仓库形成难以阅读的“毛线团”关系图。

### 7.3 调用流与数据流

用户选中函数后，查询引擎按边类型、方向、深度和置信度构建最小相关子图：调用者、被调用者、参数来源、局部赋值、返回值和外部输入输出。

V1 的数据流是跨函数、但范围和字段敏感度有限的静态数据流，不承诺完整的指向分析或运行时值追踪。界面必须区分：直接语法事实、解析到的调用、启发式框架跳转和未知动态段。

### 7.4 解释此功能

流程不是全文向量搜索后直接提问，而是：

1. 将自然语言意图拆成候选入口/实体/动作；
2. 通过全文检索、符号搜索、路由和事件索引召回种子；
3. 沿图扩展有限层级，按证据与结构相关性排序；
4. 构造大小受控的证据包；
5. LLM 输出结构化执行步骤，每一步引用节点、边或证据标识；
6. 服务端验证引用真实存在后才显示。

如果证据不足，结果应说明缺失环节并给出候选文件，不生成完整故事。

### 7.5 Git 差异模式

V1 支持三种语义明确的比较：index → working tree、HEAD → index、选定父提交 → HEAD。左右内容分别从 working tree、安全的 index blob 或 commit 对象捕获，并建立不改变项目 current 的不可变源码和事实图。初始提交使用空树；合并提交必须指定父序号；缺失浅历史和未合并 index 会显式失败。

`ChangeSet 1.1.0` 保存模式、实际左右身份、内容/清单指纹、分析配置身份、左右完整性、查询预算、文件状态、hunk、直接变化与影响路径。工作区身份包含所有实际纳入分析的受支持源码和配置内容哈希，包括未跟踪文件；秘密、忽略、不支持、二进制和超限正文不会为指纹而读取。捕获前后核验内容身份，一次有界重试后仍变化则拒绝发布；分析结束发布前再次核验并保存当时的 `current/stale/missing`。报告过期不影响历史源码阅读，但继续使用当前仓库结论前必须重算。

文件状态与 patch 来自同一比较条件和一次完整 diff，重命名使用一致阈值；限定文件时使用 literal pathspec。纯重命名没有 hunk，也不会把整文件伪装成语义变化。初始提交使用当前对象格式生成的空树，尚无提交、冲突 index、缺失合并父或浅历史均明确失败。

影响传播从旧侧删除/修改符号和新侧新增/修改符号出发，按对应图中的 `CALLS/HANDLES` 调用者或 `IMPORTS` 依赖者方向进行有预算遍历。稳定广度优先搜索选择有限的代表路径；每条路径返回有序节点、实际方向的边、证据、置信度、终点、预算和截断状态，且不得跨侧拼接。不同关系不会被包装成确定运行顺序。左右失败与排除项、无法映射变化、未知边和预算截断汇总为报告完整性；`partial` 报告仍可复核已有证据，但不能据“没有路径”断言没有影响。

输出分为：直接变化、签名或契约变化、依赖传播、可见功能面、数据或配置影响、测试覆盖提示。除非存在直接强证据，否则必须表述为“可能影响”，不能断言必然破坏。

### 7.6 所有权模式

题目模板至少覆盖：

- 找入口：某个行为最早从哪里进入；
- 追路径：某输入到副作用经历哪些步骤；
- 找变化：变量在哪里创建、改写和消费；
- 预测影响：改/删某符号可能影响什么；
- 解释分支：关键条件控制了哪条路径；
- 差异理解：本次变化改变了哪个系统契约。

每题先由确定性事实定义“证据集合 + 关键事实 + 难度”，LLM 只负责自然语言出题和语义评分辅助。用户必须从内置源码查看器选择范围生成引用。服务端验证引用的仓库、快照、文件、范围和证据归属并去重。V1 确定性评分只评价定义定位、调用方向和读写组合；离线规则无法评价的自由文本职责解释明确显示为“未评估”，关键词不会增加掌握分。

## 8. LLM 边界与契约

LLM 请求只接收经过裁剪的证据包，不直接获得完整文件系统工具。返回值使用 JSON Schema，包括：

- `claims[]`（结论）；
- 每项结论的 `evidence_ids[]`（证据标识）；
- `confidence`（置信度）；
- `unknowns[]`（未知项）；
- 可选的 `next_queries[]`（后续查询），只能由本地查询引擎执行白名单查询。

服务端必须拒绝不存在的证据标识。用户关闭远程 LLM 后，架构图、图导航、搜索、差异事实和模板化题目仍可工作，只缺少自然语言润色和语义评分。

OpenAI 首个适配器建议使用 Responses API 的结构化输出与自定义函数工具；官方文档确认该接口可以返回 JSON、调用自定义代码，并允许配置 `store`。项目默认应显式使用 `store: false`，同时保留其他提供商和本地模型适配器。[OpenAI Responses API 官方文档](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)

## 9. 隐私与威胁模型

主要风险不是传统网页注入，而是“不可信仓库内容影响分析器或 LLM”：

- 源码注释中的提示词注入内容只能作为被引用内容，不能作为指令；
- 解析器工作线程运行在受限目录和资源预算内；
- 路径解析为真实路径后，必须验证它仍位于项目根目录内；
- 不跟随越界的符号链接或目录联接；
- 默认排除 `.env*`、密钥、证书、凭据文件、第三方、构建、缓存目录和大型二进制；
- Git 地址、分支和路径不得拼接成外壳命令字符串，必须使用参数数组；
- 渲染进程不得启用 Node 集成，并开启上下文隔离和沙盒；
- 崩溃报告与遥测不包含源码。

## 10. 性能预算（V1 目标，不是已验证结果）

基准机器目标：8 核 CPU、16 GB RAM、NVMe SSD。

- 10k 文件 / 1M LOC 的常见 JS/TS/Python 项目：冷索引 P50 < 90 秒；
- 单文件保存后的增量更新：P50 < 1 秒，P95 < 3 秒；
- 已索引项目的 3-hop 子图查询：P95 < 500 ms；
- UI 首次显示可用项目概览：不等待 LLM；
- 渲染进程保持交互，所有长任务均可取消。

这些指标必须通过样例仓库与真实开源项目基准验证后才能称为达成。

## 12. 关键风险与处理顺序

| 风险 | 后果 | V1 对策 |
| --- | --- | --- |
| 动态语言无法得到完整调用图 | 用户误信错误路径 | 来源与置信度、未解析边、明确展示静态分析边界 |
| 图太大成为毛线团 | 架构图无法使用 | 分层聚类、渐进式展示、查询范围子图 |
| LLM 生成虚假链路 | 破坏产品可信度 | 证据标识结构、引用校验、LLM 不写入已验证事实 |
| 索引速度或内存失控 | 大项目不可用 | 增量哈希、工作线程、批量事务、基准门槛 |
| 源码隐私泄露 | 产品不可接受 | 本地优先、明确授权、最小片段、提供商适配器 |
| 所有权模式变成背答案 | 无法形成代码所有权 | 源码引用、变化后失效、概念掌握度、变式题 |

## 13. 开发里程碑（批准后）

### M0：最小贯通骨架

建立 Electron 安全壳、类型化 IPC、任务系统、SQLite 迁移和样例测试框架。导入一个小项目并显示文件树与索引健康状态。

### M1：证据图

将 JS、TS、Python 文件、符号、导入导出、依赖和来源信息写入数据库；架构图暂不接入 LLM。

### M2：流程浏览器

实现符号搜索、源码定位、调用图与有限数据流，完整显示置信度和未解析区段。

### M3：功能解释与差异解释

实现证据检索、结构化 LLM 解释、Git 差异块到符号的映射与影响子图。

### M4：所有权训练闭环

实现事实题模板、源码引用答题、混合评分、掌握度和快照失效机制。

### M5：系统硬化与内测版

完成真实项目基准、安全样例、崩溃恢复、取消与重试、离线模式、打包与升级测试。

每个里程碑必须可演示一条真实端到端路径，不能只交付互不连接的底层组件。

## 14. 批准前需要确认的产品决策

当前建议默认值如下，若用户批准整体方案则按这些默认值实施：

1. 首发平台：Windows 优先，但不使用只能在 Windows 运行的接口污染核心层；
2. 首发语言：JS/TS/Python；
3. 交付形态：本地桌面应用，不做账号与云同步；
4. LLM：作为可选远程能力，默认先询问项目级授权；没有 LLM 时仍可浏览事实图；
5. GitHub：V1 使用 Git 地址和系统凭据克隆，不开发 GitHub OAuth 或 GitHub App；
6. 分析语义：以静态证据为主，不执行目标项目；运行时追踪延后；
7. 数据库：每个导入项目独立 SQLite，便于删除、迁移和隔离。
