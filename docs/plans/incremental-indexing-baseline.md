# 增量索引性能基线与正确性验收设计

## 目的与范围

本计划为 V1 第三批“增量索引与性能”建立可复现的全量索引基线及增量正确性验收方案。当前文档准备批次只读取主 checkout 的实现和现有脚本，不实现增量缓存、不修改产品代码，也不产生性能测量结果。

本轮开始时主 checkout 的 HEAD 为 `64840ba9dbcf72fc71e3b1a1b27e65f2e7789662`。该 checkout 中的计划、审查记录及随后出现的其他工作区改动均由协调审查工作流维护；本轮不修改或清理它们。执行实现和测量前，必须在被授权的 checkout 重新确认代码、Git 基线和工作区状态。

本计划先处理普通本地文件夹索引。通过 Git 导入、工作区与暂存区差异、HEAD 与父提交的双侧比较以及变更影响解释属于之后独立验收的范围。本计划不安排其他操作系统的开发或验收。

### 对基线的解释

- 当前普通 reindex 路径会重新发现、读取、分析并验证项目文件。静态追踪未发现解析缓存或按文件跳过 TS/Python 分析的普通索引路径。
- 相同输入可能在完整处理后重新使用已有的不可变快照。这是快照复用，不等同于增量计算或避免了解析工作。
- `analyzing` 是粗粒度阶段；当前对外进度不提供独立的发现、读取、TS、Python、身份归一化和 SQLite 写入细分计时。`verifying` 本身还会重新发现和读取所有纳入文件。以后若需要分析器分项耗时，应在单独获批的基准工具中增加测量边界，不应从阶段名推断成本。
- 普通本地索引也会尽力读取 Git HEAD。`packages/git/src/index.ts:176-` 在不可用或失败时返回 `undefined`；因为快照规范化内容含 `gitHead`，比较结果应固定 Git 环境，或把 Git 可用/不可用作为显式环境维度记录。

## 性能测量方案

### 需要分开的路径

- **主基线**：在独立子进程中调用应用层普通本地 `indexProject()`，计全程墙钟时间、对外阶段时间、结果事实数量和进程峰值内存。这便于稳定比较后端索引成本，但不代表 Electron 端到端体验。
- **worker 诊断**：单独测量桌面分析 worker 的启动、索引完成和查询 worker 重建；将队列/IPC/worker 启动与应用层时长分开。
- **用户路径验收**：在后续真实 Electron 操作中分别计文件夹选择、导入/更新按钮到可交互状态、索引进度、查询和导航等待时间。它是 UI 验收数据，不与应用层基线混成一个指标。

### 冷/暖场景和重复次数

- **冷数据库全量索引**：每次使用新数据库/存储目录，对同一固定语料完整索引；“冷”仅表示应用持久状态为空，不表示操作系统文件缓存已清空。
- **同进程无变化 reindex**：先完成一次索引，然后对同一应用实例重复更新。当前基线仍会执行完整读取和分析，即使最终复用相同快照；后续实现需以事实正确性对照确认是否真正跳过工作。
- **重启后复用**：新进程打开已有数据库，记录打开/恢复及只读查询成本，不要与索引耗时合并。
- **稳定查询**：索引完成后分别测搜索、证据读取和有界图查询，固定查询输入、结果上限和图深度。查询运行前预热一次，再重复多次并记录每个原始样本。
- **初次建议采样**：冷索引至少 5 个独立数据库样本；reindex 与查询至少预热 1 次、测量 10 次以上。报告原始数据、中位数和 p95，并保留样本数。样本量不足以支持稳定 p95 时明确标为探索性数据，不设置先验性能阈值。

记录总时长及当前能获得的阶段事件时间。不得声称已测出 TS/Python 独立耗时、数据库同步写入时间或算法缓存命中率，除非未来工具确实增加并验证了对应的计时/计数点。内存应在独立子进程中采集；Node 主进程、分析 worker 和 Python 子进程分别报告 RSS/峰值，不能把单个 Node 进程 RSS 写成完整应用内存。采用足够短且固定的采样间隔并记录间隔及峰值采样方法。

本轮没有运行性能基线，所有性能数值保持“未测量”。首轮获得基线后再由用户/协调审查确认有证据支持的目标；不得依据一台机器或一个样本外推普遍收益。

## 正确性等价判定

### 比较方法

对同一个固定工作区状态，先用当前全量索引路径生成参考快照，再用候选增量路径生成结果；新增、修改、删除、改名及错误恢复的每种状态都必须从相同内容状态单独建立全量参考。每个阶段都比较候选结果与该状态的新鲜全量分析结果，不能只比较耗时或当前查询返回的可见子集。

1. **规范化分析事实**：使用当前 `canonicalSnapshotResult`（`packages/contracts/src/snapshot-content.ts:15-`）做顺序归一化，并按既有契约忽略快照级 ID、边/evidence 派生 ID 等指定的易变标识。比较仍必须涵盖文件和源码元数据、语言、符号、语义边、关系原因、证据路径/范围/类型、分析器 ID/版本、置信度、健康/失败完整性、配置以及 Git HEAD。对比双方须使用相同根路径、仓库、Git 环境、配置和分析器版本，避免上下文差异造成假失败或漏报。
2. **保存内容与历史不可变性**：比较实际保存的源文件相对路径、字节长度、内容 SHA-256、语言及可读源码内容的哈希；对历史快照使用 `canonicalSnapshotContent`（`packages/contracts/src/snapshot-content.ts:28-`）检查保存内容不变。还要单独检查 `createdAt` 不因旧快照重激活而改变，以及当前快照/激活元数据只在当前选择变化时更新。
3. **查询与导航**：对当前和保留的旧快照分别检查同一组搜索、图查询、证据检索与源码定位。图边深链需指向实际来源范围；旧快照内容仍应可读取，其当前工作区状态按实际内容报告为 fresh/stale/missing/unavailable。
4. **身份冲突**：相同快照 ID 若对应不同规范化事实或源码，必须拒绝持久化并保持事务原子性；不得因复用而改写旧记录。分析结果或完整性发生变化应影响快照身份。

允许的差异仅限以上规范化契约明示排除的派生 ID、集合次序及非语义的创建/激活时间字段。新增的忽略字段须有文档和契约依据，不能为让测试通过而扩宽忽略清单。

## 正确性与完整性矩阵

| 场景 | 修改序列/检查 | 等价与安全要求 |
| --- | --- | --- |
| 无变化 | A → 无变化重新索引 | 事实、证据、源码快照及查询与 A 全量参考完全一致；若当前实现复用同一 ID，验证历史 `createdAt`/内容未改写并单独报告 current 晋升。 |
| 单文件编辑 | A → 修改某文件为 B | B 与新鲜全量 B 结果等价；未改的文件证据不得保留指向错误版本的来源；相关跨文件调用/导入必须随影响变化更新。 |
| 新增/删除/改名 | A → 添加、删除或路径改名 | 目录清单、节点/边/证据与新鲜全量结果一致；本地改名按旧路径删除加新路径添加处理，不假定 Git rename 语义。 |
| 跨文件语义 | TS/JS 跨文件导入、别名、循环及调用；Python 相对包导入、模块/成员别名、循环 | 重新分析边界之外的受影响事实，关系种类、来源范围和置信等级等价；无法证明的动态目标继续是 `inferred`/`unknown`，不能因缓存升级置信度。 |
| 解析失败与恢复 | 有效源码 → 语法错误/分析器失败 → 修复；也要从 partial → complete → partial | 失败文件及受影响关系按当前失败语义保留诊断/完整性；修复后失败标记消失且结果等于完整参考。 旧快照源码、evidence 和身份不被原位改写。 |
| 配置/忽略变更 | 修改影响证据范围的 ts/js/python 配置或项目忽略设置，再还原 | 受配置影响的事实被重算；忽略文件不得从其他缓存结果泄漏事实；恢复配置后结果与对应全量快照等价。 |
| 工具/分析器环境 | 分析器版本变化；Python analyzer 不可用后恢复；本地 Git HEAD 可用/不可用 | 相关身份及完整性正确变化，失败结果不能误用旧成功结果。针对 Python 的 PATH/工具可用性变化在隔离测试环境内构造，不修改用户系统环境。普通本地路径中可选 Git HEAD 也须作为环境元数据固定或显式测试。 |
| 取消和发布边界 | 在发现、读取、分析、校验等阶段取消；观察 `persisting` 边界 | 取消不产生半成品 current 快照；已存在的完整快照/证据保持完整。进入不可中断的持久化边界后，终态应准确反映提交/取消顺序，不能既报告取消又发布候选 current。 |
| 并发/冲突 | 两个请求竞争发布，或另一个连接在校验后改变配置/当前性 | 原子性、冲突拒绝和 current 选择保持正确。待 Sol 正在修改的 graph/application/contracts 批次稳定后，再按独立验收安排此项，不在本准备任务并行改写或加测正在变化的共享文件。 |
| A→B→A 与重启 | 激活 A、索引并激活 B、返回 A、关闭后重启 | A 的 ID、原始创建时间、事实、证据和源码完全保留；B 与 A 内容身份不同；再次选择 A 只更新 current 元数据；重启后 current 和旧快照源码导航正确。 |

所有样本都应确认没有执行导入项目的代码，不运行其依赖安装、生命周期、构建、测试或仓库命令。仅运行 Project X-Ray 自身批准的分析器和测试工具。界面进度、取消和导航最终还需在后续实际 Electron 操作中验收；应用层测试不能替代该步骤。

## Git 两侧比较的后续独立门

普通本地增量基线稳定后，另起受控 Git 验收批次，单独比较工作区改动、暂存改动以及指定提交两侧快照。覆盖文件增删/纯改名/跨文件影响、某一侧分析失败、基准提交和快照身份记录，并核查变更行到符号/功能面的映射和不确定性。不得把 `benchmarks/run.ts` 当前的 Git 变更影响测量并入普通索引收益，也不得据其总时间宣称增量索引速度。

## 当前结论与未验证项

- 普通索引当前每次都会重新做全量目录发现、读取、语言分析和发布前漂移检查；快照复用发生在该流水线之后。
- 现有测试提供了可复用的身份、不可变性、失败恢复、范围变化及语言语义样例，但本准备轮没有执行测试。
- 当前 benchmark 脚本具有共享路径清理、外部网络仓库、Git 测量及共享报告覆盖行为，不能直接作为普通索引基线运行器。
- 本计划只定义未来的隔离基线与等价门槛。没有索引时延、查询时延、内存、样本规模测量或增量收益数据；没有运行测试、构建、native、dist、worker smoke 或 Electron 流程。
- 后续执行前需复核当时源码/合同是否仍与上述追踪一致，先解决/集成同时进行的图、应用层和契约修改，再在独立数据库与唯一输出中运行。
